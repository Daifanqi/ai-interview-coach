# AI模拟面试系统 —— 第4周技术方案

追问逻辑升级（Groq API裁判化）/ 语音输入 ASR（faster\-whisper 特征提取）/ 语音输出 TTS（Piper 本地合成）

## 0\. 本周范围与整体说明

本文档覆盖第4周三个模块的具体设计：追问评分从"规则打分"升级为"LLM裁判打分"、基于 faster\-whisper 的语音特征提取（语速/停顿/填充词/音量）、基于 Piper 的本地语音合成人设声线方案与流式衔接策略。

**一个需要在评审时确认的语义假设**：本文档将追问评分的 `high/low` 定义为"**回答的具体度/可追问性**"——即回答中是否存在可以继续深挖的具体细节（数据、技术选型、决策依据、个人贡献等）。`high` 触发针对具体点的深挖式追问，`low` 触发引导性追问或转下一题。如果产品设计中 `high/low` 的实际含义是"回答质量好坏"而非"具体度"，评分标准需要相应调整——这是全文的地基假设，建议第一时间和你对齐。

## 1\. 模块一：追问逻辑升级（规则打分 → Groq API 裁判）

### 1\.1 现状与目标

现有实现：用回答长度 \+ 关键词命中数做 high/low 打分，规则简单、误判率高（例如候选人堆砌关键词但内容空洞会被误判为 high；言简意赅但信息密度高的回答可能被误判为 low）。

目标：用 Groq 提供的低延迟推理，接入一个简化 prompt 做二分类裁判，替换规则打分，同时不能明显拖慢追问这条实时链路的响应时间。

### 1\.2 评分 Prompt 设计

**设计原则**：输出必须结构化、字段少、内容短——因为这是打分环节而非生成环节，多余的解释文字纯粹是浪费延迟和 token。

**System Prompt**：

```text
你是面试追问判断助手。任务：判断候选人回答相对于当前面试问题的"具体性"——
是否包含可以继续深挖的细节（如数据指标、技术选型、时间线、决策权衡、个人角色贡献、具体案例）。

判定标准：
- high：回答中出现具体的技术名词/数字/时间线/权衡决策/个人贡献等可以继续追问的实体
- low：回答空泛、套话、纯自我评价、缺乏具体细节、明显跑题，或过短（少于15个字）

只输出如下 JSON，不要输出任何解释、前缀或多余文字：
{"level":"high或low","hook":"可追问的具体点，不超过10个字；level为low时填空字符串"}
```

**User Prompt 模板**：

```text
【问题】{question}
【回答】{answer}
```

**输出 Schema**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `level` | `"high"` \| `"low"` | 二分类结果 |
| `hook` | string（≤10字） | 可供下一轮追问生成器直接引用的具体点；`low` 时为空字符串 |

只设计两个字段，是为了把输出压到最少 token（大约 15\~25 个输出 token），这是实时链路里比"让模型解释理由"更值钱的优化点。

**接入 Groq 的工程细节**：

1. **模型选择**：优先用 Groq 上的小模型（如 `llama-3.1-8b-instant` 一类的低延迟模型）做这个二分类任务，不需要用大模型——这是一个简单判别任务，小模型足够，而且直接决定这条链路的延迟下限。
2. **JSON 输出模式**：Groq 目前对严格 `json_schema`（`strict: true`，保证输出 100% 符合 schema）只在 GPT\-OSS 20B/120B 上支持；更快的 8B/接近实时的模型走的是 `json_object`（基础 JSON 语法校验，不保证严格贴合字段）或"best\-effort schema"模式。考虑到本场景对延迟更敏感、schema 本身又极简单（只有2个字段），**建议直接用 `json_object` 模式 \+ 小模型**，用严谨的 prompt 约束字段名，而不是为了 strict 保证换成更慢的 GPT\-OSS 模型。
3. **代码侧兜底（重要）**：因为 `json_object` 不保证字段一定存在/类型一定对，必须在代码里做：JSON 解析失败 → 正则兜底提取 `high`/`low` 关键字 → 都失败则降级回原有的"长度\+关键词"规则打分，绝不能因为一次 LLM 调用失败而让追问链路整体挂掉。
4. **输入截断**：为控制输入 token，若候选人回答过长（如超过 300 字），只取前 200 字 \+ 末尾 50 字拼接（开头通常包含论点，结尾通常包含结论/量化结果），而不是整段塞进去。
5. **超时与延迟预算**：建议给这次调用设置一个较短的超时（如 800ms\~1.2s），超时直接走规则打分兜底——追问节奏不能被一次 API 抖动拖垮。

### 1\.3 是否需要考虑人设差异？

这里有两种做法，取舍点不同：

| 方案 | 说明 | 延迟增量 | 维护成本 | 准确度收益 |
| --- | --- | --- | --- | --- |
| A. 统一 prompt，人设无关 | 所有人设共用同一套"具体性"判断标准 | 无 | 低（一套 prompt） | 基准水平，但不同人设的"追问触发点"可能不够贴合人设气质 |
| B. 人设专属 prompt | 技术挖掘型/亲和型/严格型各一套独立 prompt 和标准 | 略增（prompt 更长） | 高（3套 prompt 要分别维护、分别评估） | 更贴合人设，但增加了"哪套 prompt 判断错了"的排查复杂度 |
| C（推荐）. 共享主干 \+ 人设化的一小段附加标准 | 核心 JSON schema 和主干标准不变，只在 system prompt 末尾插入一小段随人设变化的判定倾向 | 几乎无（多10\~20个token） | 低（一份模板 \+ 3段短文案） | 接近方案B的收益，复杂度接近方案A |

**推荐方案 C**，理由：`level` 这个二分类是一个必须快、必须稳的**门控信号**，不适合承载太多人设逻辑的分支复杂度；而人设气质更适合作用在"追问问题怎么问"（下游的追问生成 prompt），而不是"要不要追问"这个判断本身。用同一套主干 \+ 小段可插拔文案，既保留了人设差异化的空间，又不让打分环节变成三套要分别调优、分别踩坑的独立系统。

具体的人设附加文案示例（拼接进 system prompt 末尾）：

```text
# 技术挖掘型追加标准
对"技术具体性"要求更高：必须包含技术选型、架构设计、量化指标（性能数据/规模数字）
中的至少一项才能判定为 high；纯流程描述不算。

# 亲和型追加标准
更看重语言的真实感和个人化程度：第一人称具体经历、带有真实细节的表达（哪怕不够
"技术"）判定为 high；明显背诵式、模板化的回答即使包含关键词也判定为 low。

# 严格型追加标准
重点关注回答是否直接、逻辑自洽：如果回答存在回避问题、自相矛盾、或对具体问题给
泛泛而谈的回应，判定为 low，即使包含个别专业词汇。
```

工程上只需要在拼装 system prompt 时按当前人设插入对应段落，`level`/`hook` 的输出 schema 完全不变，调用方式、解析逻辑、兜底逻辑三个人设共用一套代码。

## 2\. 模块二：语音输入（ASR，faster\-whisper 本地）

### 2\.1 总体流程

音频 → faster\-whisper 转写（开启 `word_timestamps=True` 获取词级时间戳）→ 文本用于内容分析（含模块一的追问评分）；时间戳和原始波形分别用于计算语速、停顿、填充词、音量四个特征，四者是并行的旁路特征提取，不阻塞主转写文本的产出。

### 2\.2 语速计算公式

**统计口径**：中文按字符数，英文按单词数——这是两种语言天然的计量单位，强行统一成"字数"或"词数"都会失真，所以分别统计，再在需要跨语言比较时做归一化。

设某段回答的有效时长为 `D`（秒，取该段转写的起止时间戳之差，包含回答内部的短停顿，不含首尾静音）：

- 中文字符数 `C`：转写文本中匹配 Unicode 范围 `一-鿿` 的字符数量（不含标点、数字、字母）
- 英文单词数 `W`：转写文本中按空白切分、且不含中文字符的字母数字 token 数量

**分语言主指标**（面向产品展示，直观易懂）：

- 纯中文回答：语速 \= `C / (D/60)`，单位**字/分钟（CPM）**
- 纯英文回答：语速 \= `W / (D/60)`，单位**词/分钟（WPM）**

**中英混合回答的统一内部指标**：由于中文字符本身接近一个音节，英文单词平均音节数按经验值取 1.3，构造一个跨语言可比的"音节/分钟"指标，仅用于内部阈值判断和中英混合场景，不作为面向用户展示的主指标：

```math
\text{SRI（音节/分钟）} = \frac{C \times 1.0 + W \times 1.3}{D / 60}
```

**是否要剔除停顿时间**：这里故意**不**从 `D` 里剔除内部停顿时间。原因是停顿本身也是一个独立特征维度（见2.3节），如果语速指标本身又把停顿减掉，会让"语速慢"和"停顿多"这两种不同成因被压缩成同一个数字，不利于后续做候选人表现的归因分析。第4周只上线这个"含停顿的粗语速"，"净发音速率"（剔除停顿后的真实语速）留作二期，产品上线后有真实数据再决定是否需要。

**参考区间**（经验值，仅供工程实现时设阈值参考，**上线后需要用实际候选人录音样本重新校准**，不同人设/不同题型的正常语速本身也可能不同）：

| 语言 | 偏慢 | 正常 | 偏快 |
| --- | --- | --- | --- |
| 中文 | \< 180 字/分钟 | 180 \~ 260 字/分钟 | \> 260 字/分钟 |
| 英文 | \< 100 词/分钟 | 100 \~ 150 词/分钟 | \> 150 词/分钟 |

### 2\.3 停顿特征

不依赖 VAD 的分段结果，直接用 `word_timestamps=True` 返回的词级时间戳计算：相邻两个词 `word[n+1].start - word[n].end > 阈值`（建议 300ms）即记一次停顿。由此得到四个子特征：停顿次数、停顿总时长、最长单次停顿、平均停顿时长。

**faster\-whisper 的 VAD 需要单独调优**：其默认 VAD（基于 Silero VAD）行为偏保守，只在静音较长时才切分/丢弃音频，对 300ms\~1s 这种"思考停顿"不够敏感。建议：转写阶段保留默认或接近默认的 VAD 设置以保证转写准确率；但停顿特征的计算完全走词级时间戳这条独立路径，不依赖 VAD 的切分结果，避免两者互相影响。另外需要专门测试 `vad_filter=True` 是否会把一段独立的语气词（比如单独一句"嗯……"）当作静音丢掉，如果丢弃会直接导致填充词漏检，这个需要在测试阶段用真实样本验证。

### 2\.4 填充词检测

**中文**：

| 类别 | 词表 | 判定方式 |
| --- | --- | --- |
| 强填充词（几乎总是填充） | 嗯、啊、呃、诶、哦 | 出现即计数 |
| 弱填充词（需结合语境） | 这个、那个、就是、就是说、然后、其实、怎么说呢、你知道吧、对吧、是吧、这样子 | 仅当该词前后存在停顿（\>300ms）或该词在句中孤立出现（前后紧邻逗号/停顿）时计数，避免把"这个方案就是我做的"这类正常语义用法误判为填充词 |

**英文**：

| 类别 | 词表 | 判定方式 |
| --- | --- | --- |
| 强填充词 | um, uh, uhh, umm, er, erm | 出现即计数 |
| 弱填充词 | like, you know, I mean, sort of, kind of, basically, actually, so, right, well | 同上，结合停顿/孤立出现的上下文规则 |

弱填充词之所以要看上下文，是因为它们本身也是正常词汇（"这个"可以是指示代词，"actually"可以是转折副词），单纯做字符串匹配会有明显的误报率；用词级时间戳判断"是否伴随停顿/是否孤立"是一个成本很低但能大幅降噪的做法。

### 2\.5 音量变化特征

这个特征不从 ASR 文本或时间戳中获取，而是直接对原始 PCM 波形处理：按固定窗口（建议 200ms）计算 RMS 或转换为 dBFS，得到一条音量曲线。第4周先实现两个简单统计量作为 MVP：

- **音量标准差**：反映整体音量是否忽高忽低（不稳定）
- **相对基线的音量偏差**：以回答前几秒的平均音量为基线，观察是否有明显的持续走低（可能与信心不足相关）或突然拔高

更复杂的语调/信心推断（如判断"结尾降调"这类韵律特征）建议放到后续迭代，第4周先把基础的音量统计量跑通、和其余三个特征拼进同一份候选人表现报告里。

## 3\. 模块三：语音输出（TTS，Piper 本地合成）

### 3\.1 三种人设的声线选择

**英文（en\_US / en\_GB）**：Piper 官方声线库中英文声线选择较丰富，可以为三种人设分别选出音色区分度明显的声线：

| 人设 | 推荐声线 | 备选 | 选择理由 |
| --- | --- | --- | --- |
| 亲和型 | `en_US-amy-medium` | `en_US-hfc_female-medium` | 女声，语调自然温和，是 Piper 里最常用的通用友好女声 |
| 技术挖掘型 | `en_US-ryan-high` | `en_US-lessac-medium` | 男声，咬字清晰、语调中性克制，适合"就事论事"式的技术追问场景；`lessac` 是 Piper 训练时常用的标准中性基准声，备选时可用 |
| 严格型 | `en_GB-alan-medium` | `en_US-norman-medium` | 英式口音天然带一点更正式/更有距离感的气质，适合严格型考官；`norman` 声音更低沉，作为不想用英式口音时的替代 |

**中文（zh\_CN）**：

**需要明确一个限制**：Piper 官方声线库里，中文（zh\_CN）目前只有 **`huayan`** 一个音色（`x_low`/`medium` 两档质量），没有第二个官方中文声线可选。这意味着"三种人设各配一个不同中文声线"在当前 Piper 官方目录下**做不到**。

第4周的应对方案：**统一使用 `zh_CN-huayan-medium`，通过合成参数差异化制造人设区分度**，而不是切换音色本身：

| 人设 | `length_scale`（语速，越大越慢） | `noise_scale`（韵律变化幅度） | `noise_w`（音素时长随机性） | 听感目标 |
| --- | --- | --- | --- | --- |
| 亲和型 | 1\.08（略慢） | 0\.75（略高） | 0\.85 | 更从容、语调起伏更自然温和 |
| 技术挖掘型 | 1\.00（标准） | 0\.60（中等） | 0\.70 | 中性清晰，不带明显情绪色彩 |
| 严格型 | 0\.92（略快） | 0\.50（偏低） | 0\.60 | 更干脆平稳，情绪起伏少，显得克制严肃 |

需要如实说明：这种参数化差异**能带来可感知但幅度有限的区分度**，不等同于换了一个新音色，实际听感效果建议做完之后找几个人盲听打分评估是否达到产品预期。如果评估下来区分度不够，后续可选的方向（**不在第4周范围内，先记录为待评估项**）：

1. 在 Hugging Face（`rhasspy/piper-voices` 或社区仓库）寻找是否有除 `huayan` 外的社区训练中文声线，需要单独调研可用性和质量，本周未验证；
2. 引入其他本地 TTS 引擎（如 CosyVoice、GPT\-SoVITS）获得更多中文音色选择——这属于更大的技术选型变更，建议作为独立技术评估任务排期，不是"加一行配置"能解决的；
3. 通过后期音频处理（如轻度变调）在 `huayan` 基础上进一步做区分，会引入额外处理延迟和音质损耗，第4周不做。

### 3\.2 语音合成与大模型回复的流程衔接

**方案对比**：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 全量等待 | 等大模型完全生成完整段回复文字，再整体传给 Piper 合成，合成完再播放 | 实现简单；语调连贯性最好 | 总延迟 \= LLM生成时间 \+ TTS合成时间，两者串行叠加，回复越长用户等待感越强 |
| B（推荐）. 分句流式 | LLM 流式吐字过程中按句子边界切分文本块，逐块推入 TTS 合成队列，播放器按序播放，首句合成完即可开始播放，无需等全部文本生成完 | 首次出声延迟大幅降低，尤其在长反馈/总结场景收益明显 | 需要处理分句边界、片段过短/过长、播放顺序等工程细节 |

**推荐方案 B 的具体设计**：

1. **文本缓冲与切分**：维护一个文本缓冲区，持续接收 LLM 流式输出的 token；遇到中文「。！？」或英文 `. ! ?` 视为候选切分点。
2. **片段长度控制**：切分点命中后不立即切分，还要检查片段长度——中文短于6字/英文短于4词时，先合并到下一个标点再切（避免出现"好的。"这种过短破碎片段导致听感割裂）；中文超过40字/英文超过25词时，在最近的逗号或空格处强制截断（避免因为一句话过长导致首包延迟仍然很大）。
3. **误判规则**：数字小数点、英文缩写、版本号中的句点（如 `3.14`、`e.g.`、`v2.0`）不应被当作句子结尾，第4周用正则规则覆盖常见 case 即可，不引入额外的句子边界检测模型。
4. **合成与播放队列**：文本片段带序号推入 TTS 任务队列，TTS worker（可视资源情况开1\~2个并行）异步合成，合成结果按序号放入播放队列；播放器只要队列不空就持续播放，实现"LLM还在生成后半段文字，前半段的语音已经在播"的效果。
5. **短回复走简化路径**：追问问题生成这类场景本身通常只有1\~2句、生成本身就快，走流式分句的收益有限，反而增加工程复杂度和边界情况处理成本——建议对这类短回复场景直接走"等待完整生成后一次性合成"的简单路径；只有在生成面试总结/长反馈这类较长文本时，才启用完整的分句流式方案。这样可以把工程复杂度花在真正有收益的场景上。

## 4\. 风险与待验证项

以下几项建议在开发和测试阶段专门验证，本文档中给出的是工程上合理的起点值，不是最终定论：

| 待验证项 | 说明 |
| --- | --- |
| `high/low` 语义对齐 | 本文档假设为"回答具体度"，需要和产品设计确认是否与追问触发逻辑的预期一致（见第0节假设说明） |
| Groq 结构化输出的容错 | `json_object` 模式不保证字段严格存在，代码侧的解析失败兜底/降级规则打分逻辑必须覆盖测试到 |
| 中文声线区分度 | 参数化差异化的实际听感效果需要真人盲听评估，可能不足以满足产品预期 |
| 语速/停顿阈值 | 文档中的经验区间需要用真实候选人录音样本重新校准 |
| VAD 对短停顿/填充词的影响 | 需要实测 `vad_filter` 开关和 `vad_parameters` 调整对填充词检出率的影响 |
